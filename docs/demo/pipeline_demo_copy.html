The problem area, and why we chose it

Con Edison runs EV-charger programs where chargers are installed and managed by external contractors. Data arrives through third-party integrators — and it is frequently late, incomplete, inconsistent, and unstructured, in multiple formats from multiple sources.

Today, cleansing, reconciliation, structuring, and reporting are manual, causing delays that jeopardize strict PSC (Public Service Commission) mandates to report accurately and on time. We chose this area because it is a real, high-stakes operational problem where AI can demonstrably remove manual work — and where a wrong number has regulatory consequences.

Background research — and one surprising fact

We studied how charger data actually behaves across the industry: station registries (AFDC/NREL), municipal charging-session logs, and unstructured contractor reports. The literature and public datasets agree on one thing: the data is messier than anyone budgets for — unit swaps (W vs kW), date-format chaos, free-text connector names, and late-arriving files are the norm, not the exception.

⚡
Surprising fact: in the official NYC DOT dataset we tested — supposedly "clean" municipal data — the pipeline still found 10,457 duplicate records (≈4%), 16,157 conflicting field values that no single source could resolve, and one unresolved SAFETY maintenance event hiding in plain sight. The mess isn't in exotic files; it's in the data you already have.
3

Ideation process

We designed the project as a five-phase pipeline, each phase owned by one person and one agent session, all running in parallel on separate branches:

P1 · Ingestion

Parse everything

Readers for every format, LLM extraction of maintenance events from contractor text, a deterministic messiness injector for testing.

P2 · Validation

Fix what's fixable

A declarative YAML rule engine, standardizers (dates, units, enums), missing-data derivation, quality scoring per record.

P3 · Reconciliation

One source of truth

Entity resolution across sources, conflict resolution into golden records, anomaly and safety detection.

P4 · Reporting

Regulatory output

PSC compliance report with audit-trail lineage, operations dashboard, safety triage, customer-experience view.

P5 · Platform

Make it a product

Orchestrator, health monitoring, integration harness, merge-readiness gate — and the human integration manager.

The enabling decisions: a frozen canonical schema and frozen CLI contract so five people never block each other; every module developed against its own fixtures; and the whole plan adversarially reviewed for task overlap and merge safety before anyone wrote code.

What failed — honestly

The brief asks what failed, so here is the list — each item was found, fixed, and tested:

§6 protocol deviations found at merge review.

Two stages (P1 and P2) emitted their final metrics line only under a flag and skipped corrupt input lines instead of hard-failing. The Integration Manager's contract harness caught both (commits d33f684, 640ee4f) — a reminder that "works on my fixtures" is not the contract.

A config bug that looked like correct output.

The severity synonym urgent-safety normalized to MAJOR instead of SAFETY, because the shorter synonym urgent matched first. Only hand-verifying every fixture line caught it.

Near-public privacy leak.

Git auto-configured a commit author with a student's NYU username and wireless hostname — which would have been permanently public in a fork. Caught before push; fixed with the GitHub no-reply address.

The schema vs. "never drop a record" conflict.

A record missing a required provenance field cannot exist in the frozen P2 schema. Resolution: flag it, emit it anyway with a marker, and stash dropped values as raw_<field> extras — no data lost, no contract broken silently.

The LLM path was never live-tested.

No API key in the development environment, so all runs used the deterministic fallback. The LLM path is implemented, counted, and fails safe — but "untested live" is a fact, not a feature.

Reconciliation is the bottleneck.

The hardest run spent ~74 of 75 minutes in fuzzy matching (4,417s). Correct, but it sets the budget for nightly runs.

5

What did not fail — what the solution looks like

A four-stage pipeline, one command, full audit trail:

  • Ingestion parses all three formats and turns unstructured contractor text into typed records via LLM extraction with a deterministic fallback.
  • Validation & cleaning repairs what is repairable — W→kW, Wh→kWh, date-format chaos ("3/4/24 2pm" → ISO-8601 with timezone), free-text enums ("chgpt LVL2 dual" → CHAdeMO / L2) — derives missing values, and scores every record 0–1 with stable issue codes.
  • Reconciliation resolves the same physical charger across sources into golden records, logging every conflict decision, and detects anomalies statistically.
  • Reporting renders the PSC compliance report with a data-lineage appendix (so "accurate and on time" is demonstrable), an operations dashboard, a safety triage, and a customer-experience view.

The result on the real run: 258,343 raw records → 247,886 golden records, every decision attributable, every problem counted in per-stage reports — offline, deterministic, and re-runnable.

The shape of the answer Don't replace the analysts. Remove the manual data scramble: automated cleansing and reconciliation compress days of spreadsheet work into a 75-minute offline run with a paper trail regulators can audit.

Our recommendation to Con Edison

  1. Adopt the pipeline as the PSC reporting path. Run it on every late-arriving batch: deterministic reruns supersede prior golden records, and the lineage appendix makes "accurate and on time" auditable.
  2. Start with validation + reporting on live data, LLM extraction off by default (--no-llm): the deterministic path already delivers most of the value at zero marginal cost.
  3. Keep a human in the loop for SAFETY anomalies only. Everything else — duplicates, conflicts, outliers — can auto-resolve with a logged decision.
  4. Instrument it. Pipeline-health metrics per stage (records, duration, LLM usage) already ship with every run.
  5. Then extend: plug in contractor-portal feeds, add alerting on the anomaly feed, and schedule nightly reconciliation (the 74-minute matching step is the capacity planner's number).
8

What could go wrong

  • Model/provider drift. LLM extraction quality and pricing change without notice; the fallback path and pinned model configuration mitigate, but monitoring is mandatory.
  • Schema drift. A new integrator format or a changed field meaning silently shifts interpretation — the frozen-schema proposal process exists, but someone must run it.
  • Late-arriving data at the deadline. A file landing after the report window forces a restatement; the pipeline supports it, but the process must allow it.
  • Scale. Reconciliation took 74 minutes at 258k records; annual growth or full-state rollout needs the matching step optimized or sharded.
  • Overtrust. A 0.99-quality score is not ground truth. Analysts must be able to see why — the issue codes, conflict logs, and raw-value stashes exist for exactly that.
  • Credential hygiene. Keys live only in the environment, never in the repository; the pipeline scans every submission for them — but a leak elsewhere still burns a key.
  • Privacy/public-work rules. Anything pushed to a public fork is public; identifiable field media and private feedback must stay on private channels.
