1

The problem

Why EV-charger data is a reporting liability today — and why it doesn't have to be.

Con Edison's EV-charger programs depend on external contractors whose data arrives through third-party integrators. It is frequently late, incomplete, inconsistent, and unstructured — and today, turning it into a regulatory report is a manual process that strains PSC mandates to report accurately and on time.

🔌

Charging sessions

Structured CSV logs — but with date-format chaos, W/kW unit swaps, and missing fields.

🗺️

Station registry

GeoJSON/API dumps with free-text connector names and conflicting coordinates.

📄

Contractor reports

Unstructured email and fault digests that only a human (or an LLM) can read.

2

Background research

What the data itself told us — and the findings that shaped every design decision.

Before proposing a fix, we studied how the problem actually behaves in the wild: the formats, the failure modes, and the patterns that keep showing up across datasets. The goal was to design for the real world, not for a clean-room example.

Across public datasets and industry material, one pattern dominates: the mess is in the data you already have, not in exotic formats. Unit swaps, date chaos, free-text enums, and late-arriving files are the norm. The fix therefore had to be a pipeline of small, testable stages — not one clever model.

⚡
One surprising fact. In the official NYC DOT dataset — supposedly clean municipal data — our pipeline still found 4,105 duplicate records (≈1.6%), 2,731 conflicting field values no single source could resolve, and three unresolved SAFETY maintenance events hiding in plain sight. The cost of not looking is regulatory.
3

Ideation process

Five phases, designed to run in parallel without ever blocking each other — then merged into one pipeline.

P1 · Ingestion

Parse everything

Parsing every format and extracting structure from contractor text with an LLM.

P2 · Validation

Fix what's fixable

Declarative YAML rule engine; standardizers; missing-data derivation; per-record quality scores.

P3 · Reconciliation

One source of truth

Merging records from different sources that describe the same charger, into one trusted answer.

P4 · Reporting

Regulatory output

PSC report with lineage appendix; operations dashboard; safety triage; customer-experience view.

The enabling decisions Set the rules first, then wrote the code. Agreed on the data format and how every command works — before anyone started. let five builders work in parallel on separate branches; Everyone tested with their own sample data, and then we put it all together at the end. A fifth phase (P5) wraps it all in an orchestrator with health monitoring and an integration harness.
4

What failed

The honest list. Every item below was found, fixed, and re-tested.

✕
Contract-protocol deviations caught at merge review.

Two stages emitted their final metrics line only under a flag and skipped corrupt input instead of hard-failing. The automatic checks caught both (d33f684, 640ee4f) — a reminder that "works on my fixtures" is not the contract.

✕
A config bug that looked like correct output.

The severity synonym urgent-safety normalized to MAJOR instead of SAFETY, because the shorter synonym urgent matched first. Only hand-verifying every fixture line caught it.

✕
A near-public privacy leak.

Git auto-configured a commit author with a student's NYU username and wireless hostname — permanently public in a fork. Caught before push; fixed with the GitHub no-reply address.

✕
"Never drop a record".

A record missing a required provenance field cannot exist in the P2. Resolution: flag it, emit it anyway with a marker, and stash raw values as raw_<field> extras — nothing lost, nothing silently broken.

Our recommendation

Five steps to turn this into Con Edison's reporting backbone.

1

Adopt the pipeline as the PSC reporting path. Run it on every late-arriving batch: deterministic re-runs supersede prior golden records, and the lineage appendix makes "accurate and on time" auditable.

2

Start with validation + reporting on live data, LLM off by default. The deterministic path already delivers most of the value at zero marginal cost.

3

Keep a human in the loop for SAFETY anomalies only. Everything else — duplicates, conflicts, outliers — auto-resolves with a logged decision.

4

Instrument it. Per-stage health metrics (records, duration, LLM usage) ship with every run — alerting on the anomaly feed is a small next step.

5

Then extend. Contractor-portal feeds, nightly scheduling, and sharding the matching step.

What could go wrong

We named the risks so they can be managed instead of discovered.

Model & provider drift

LLM quality and pricing change without notice. Mitigation: pinned model config, deterministic fallback path, and usage monitoring.

Schema drift

A new integrator format or changed field meaning silently shifts interpretation. The proposal process exists — someone must run it.

Late-arriving data at the deadline

A file landing after the report window forces a restatement. The pipeline supports it; the process must allow it.

Scale

Now 2.2 minutes at 258k records after the audit-driven fix. Full-state rollout keeps the same architecture — the bottleneck was the matching predicate, not the pipeline.

Overtrust in scores

A 0.99 quality score is not ground truth. Issue codes, conflict logs, and raw-value stashes exist so analysts can always see why.

Credential & privacy hygiene

Keys live only in the environment; the pipeline scans every submission for them. Identifiable field media stays off public channels.
