The problem

Why EV-charger data is a reporting liability today — and why it doesn't have to be.

Con Edison's EV-charger programs depend on external contractors whose data arrives through third-party integrators. It is frequently late, incomplete, inconsistent, and unstructured — and today, turning it into a regulatory report is a manual process that strains PSC mandates to report accurately and on time.

🔌

Charging sessions

Structured CSV logs — but with date-format chaos, W/kW unit swaps, and missing fields.

🗺️

Station registry

GeoJSON/API dumps with free-text connector names and conflicting coordinates.

📄

Contractor reports

Unstructured email and fault digests that only a human (or an LLM) can read.

2

Background research

We studied how charger data actually behaves across the industry — registries, municipal logs, and contractor text.

Across public datasets and industry material, one pattern dominates: the mess is in the data you already have, not in exotic formats. Unit swaps, date chaos, free-text enums, and late-arriving files are the norm. The fix therefore had to be a pipeline of small, testable stages — not one clever model.

⚡
One surprising fact. In the official NYC DOT dataset — supposedly clean municipal data — our pipeline still found 10,457 duplicate records (≈4%), 16,157 conflicting field values no single source could resolve, and one unresolved SAFETY maintenance event hiding in plain sight. The cost of not looking is regulatory.
3

Ideation process

Five phases, designed to run in parallel without ever blocking each other — then merged into one pipeline.

P1 · Ingestion

Parse everything

Readers for every format; LLM extraction from contractor text; deterministic messiness injector.

P2 · Validation

Fix what's fixable

Declarative YAML rule engine; standardizers; missing-data derivation; per-record quality scores.

P3 · Reconciliation

One source of truth

Entity resolution across sources; conflict resolution into golden records; anomaly & safety detection.

P4 · Reporting

Regulatory output

PSC report with lineage appendix; operations dashboard; safety triage; customer-experience view.

The enabling decisions A frozen canonical schema and a frozen CLI contract let five builders work in parallel on separate branches; every module was developed against its own adversarial fixtures; and the plan was reviewed for overlap and merge safety before a line of code was written. A fifth phase (P5) wraps it all in an orchestrator with health monitoring and an integration harness.

What failed

The honest list. Every item below was found, fixed, and re-tested.

✕
Contract-protocol deviations caught at merge review.

Two stages emitted their final metrics line only under a flag and skipped corrupt input instead of hard-failing. The integration harness caught both (d33f684, 640ee4f) — a reminder that "works on my fixtures" is not the contract.

✕
A config bug that looked like correct output.

The severity synonym urgent-safety normalized to MAJOR instead of SAFETY, because the shorter synonym urgent matched first. Only hand-verifying every fixture line caught it.

✕
A near-public privacy leak.

Git auto-configured a commit author with a student's NYU username and wireless hostname — permanently public in a fork. Caught before push; fixed with the GitHub no-reply address.

✕
"Never drop a record" vs. the frozen schema.

A record missing a required provenance field cannot exist in the P2 schema. Resolution: flag it, emit it anyway with a marker, and stash raw values as raw_<field> extras — nothing lost, nothing silently broken.

✕
The LLM path was never live-tested — and reconciliation is slow.

No API key in the dev environment, so all runs used the deterministic fallback (implemented, counted, fail-safe — but untested live). And fuzzy matching took ~74 of 75 minutes on 258k records: correct, but the capacity planner's number.

What worked — the solution

One command, four stages, a full audit trail — and every decision attributable.

  • Ingestion turns unstructured contractor text into typed records (LLM extraction with a deterministic fallback) and normalizes all sources to one canonical JSONL.
  • Validation & cleaning repairs what's repairable — W→kW, Wh→kWh, "3/4/24 2pm" → ISO-8601 with timezone, "chgpt LVL2 dual" → CHAdeMO / L2 — derives missing values, and scores every record 0–1 with stable issue codes.
  • Reconciliation resolves the same physical charger across sources into golden records, logs every conflict decision, and detects anomalies statistically (duplicate billing, energy outliers, silent chargers).
  • Reporting renders the PSC compliance report with a data-lineage appendix — so "accurate and on time" is demonstrable — plus an operations dashboard, safety triage, and customer-experience view.
The shape of the answer Don't replace the analysts. Remove the manual scramble: automated cleansing and reconciliation compress days of spreadsheet work into a 75-minute offline run with a paper trail regulators can audit.

Our recommendation

Five steps to turn this into Con Edison's reporting backbone.

1

Adopt the pipeline as the PSC reporting path. Run it on every late-arriving batch: deterministic re-runs supersede prior golden records, and the lineage appendix makes "accurate and on time" auditable.

2

Start with validation + reporting on live data, LLM off by default. The deterministic path already delivers most of the value at zero marginal cost.

3

Keep a human in the loop for SAFETY anomalies only. Everything else — duplicates, conflicts, outliers — auto-resolves with a logged decision.

4

Instrument it. Per-stage health metrics (records, duration, LLM usage) ship with every run — alerting on the anomaly feed is a small next step.

5

Then extend. Contractor-portal feeds, nightly scheduling, and sharding the matching step (the 74-minute number is the capacity planner's input, not a blocker).

What could go wrong

We named the risks so they can be managed instead of discovered.

Model & provider drift

LLM quality and pricing change without notice. Mitigation: pinned model config, deterministic fallback path, and usage monitoring.

Schema drift

A new integrator format or changed field meaning silently shifts interpretation. The proposal process exists — someone must run it.

Late-arriving data at the deadline

A file landing after the report window forces a restatement. The pipeline supports it; the process must allow it.

Scale

74 minutes at 258k records. Full-state rollout needs the matching step optimized or sharded — planned, not started.

Overtrust in scores

A 0.99 quality score is not ground truth. Issue codes, conflict logs, and raw-value stashes exist so analysts can always see why.

Credential & privacy hygiene

Keys live only in the environment; the pipeline scans every submission for them. Identifiable field media stays off public channels.
